# 計画の点検の一覧

planner は計画を出す前にこの一覧で自己点検し、plan-reviewer は同じ一覧で審査する。
**同じ一覧を 2 つの役割が使うので、ここが唯一の置き場所である**（以前は 2 つのプロンプトに写していた）。

**一覧が持つのは「満たすべき条件」だけで、直し方は書かない。** 直し方は同じ skill の `references/format.md` と
planner のプロンプトにある。ここに直し方を足すと、plan-reviewer には自分への指示に読めてしまう。

<!-- checklist:start -->
- [ ] **issue の完了条件がすべて `AC` に対応している。** issue が「〜が残っている」と求めているのに、
      状態だけを見る条件しか無い、が起きやすい（実機で差し戻された形）
- [ ] **対応表が両方向で埋まっている。** `AC` の付かない `US` と、`US` に付かない `AC` が無い
- [ ] **INVEST を満たす。**
      - **I**ndependent: 他の作業や他のストーリーの成果を待たずに出せる
      - **N**egotiable: ストーリーにファイル名・クラス名・コマンドを書いていない（実装方針の仕事）
      - **V**aluable: 受け手の利益が書かれている（「〜を実装する」は手段であって価値ではない）
      - **E**stimable: 見積もれる粒度
      - **S**mall: 1 PR（目安はテストを除いて 20 ファイル、含めて 40 ファイル）に収まる。
        収まらないなら、切った軸の分かる分割案がある
      - **T**estable: 満たしたと確かめる方法がある
- [ ] **触ってはいけない領域が変更対象に入っていない。** `.github/workflows/**`、`.agent/**`、
      `.claude/**`、`.agent/conventions.md` が挙げている禁止領域
- [ ] **規模判定の 2 つの数が変更対象の数と一致している**（テストを除いた数と、含めた数）。
      **「上限超過」の語があるのは、上限を超えているときだけ**である
- [ ] **画面とユースケースが節として分かれ、`## 前提` に混ざっていない。** 画面のパスは実在する
      ルーティングから引いた（推測で書いていない）。画面を持たない変更なら「該当なし」と書いた
- [ ] **`automated` の `command` がこのリポジトリで実際に走る形になっている**（規約の「テスト」節と
      整合）。`manual` の項目は、**CI が走らせている経路が無く**、`evidence` の引き方が
      条件に含まれている
- [ ] **実在するデータで落ちない条件になっている。** 金額・数量は 0・負・上限のどれかを踏む。
      保存済みデータの意味を変える変更なら、**変更前のデータが入った状態**の条件がある
- [ ] **前提が推測で埋まっていない。** 決められなかったことは「未確認」として残り、判断の記録
      （`status: open`）にも選択肢と推奨がある
- [ ] **`## 前提` で「決めたこと」と「未確認」が分かれている。** 混ざっていない。未確認には
      行ごとに本文での残し方がある。**`## 変更対象` と重なる記述が入っていない**
- [ ] **受け入れ条件が要求することの根拠が、計画の中に挙がっている。** `AC` が「〜と書かれている」
      「〜が動く」を求めるなら、その裏を取れるファイルが `## 変更対象` か、計画が根拠として挙げた
      一覧に入っている
- [ ] **根拠の「本数」を書いていない**（`## 禁止` を見る）。「7 本」「9 ファイル」のような数が
      計画にも受け入れ条件にも無い。**数を増やして辻褄を合わせたものは、直っていない**
<!-- checklist:end -->

**この一覧を `plan.md` に書き写さない。** 目的は直すこと（または「未確認」として前提に出すこと）で、
チェック済みの宣言を成果物に増やすことではない。
