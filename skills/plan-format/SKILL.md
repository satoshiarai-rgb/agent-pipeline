# plan.md と acceptance.json の形式

planner の成果物の形式はここが正である。**進め方（何を調べ、何を問い、誰に答えさせるか）は
planner のプロンプトにあり、ここには書かない。** ここにあるのは、決まったことをどういう形で
書き出すかだけである。

## `plan.md`

**節の順序はこのとおり**（承認する人が「誰のために何が変わるか → どこがどう変わるか → 何を確かめるか → どう作るか」の
順に読めるように。ファイルの一覧は最初に読むものではないので後ろ）。

```markdown
# 計画: <issue のタイトル>

## ユーザーストーリー

- **US-12-1**: <誰> として、<何をしたい>。<なぜ（それで何が良くなるか）>

## 要件の詳細化

## 対象の画面

| # | 画面 | パス | 出る場所 | いま | これから |
|---|---|---|---|---|---|
| S-12-1 | <画面名> | `GET /path` | <その画面のどこか> | <いまの見え方> | <これからの見え方> |

## ユースケース

| # | 誰が何をすると | いま | これから | 画面 | ストーリー |
|---|---|---|---|---|---|
| UC-12-1 | <操作> | <いまの振る舞い> | <これからの振る舞い> | S-12-1 | US-12-1 |

## 前提

### 決めたこと

| 決めたこと | 判断の記録 |
|---|---|
| <1 行> | `<slug>` |

### 未確認

| 未確認 | 本文での残し方 |
|---|---|
| <1 行> | <`TODO` の 1 行 / `status: need-action` など> |

## 実装方針

| # | すること | 先に要るもの |
|---|---|---|
| 1 | <着手点> | — |
| 2 | <次の手> | 1 |

## 受け入れ条件

| ストーリー | 満たす受け入れ条件 |
|---|---|
| US-12-1 | AC-12-1, AC-12-3 |

## 変更対象

| ファイル | 種別 | 変更内容 |
|---|---|---|
| `path/to/file.ts` | 変更 | <何をどう変えるか> |
| `path/to/file_test.ts` | テスト | <何を確かめるテストか> |

## 規模判定

| | テストを除く | テストを含む |
|---|---|---|
| 変更ファイル数見込み | N | M |
| 上限 | 20 | 40 |
```

**ID には issue 番号を含める**（issue #12 なら `US-12-1` / `S-12-1` / `UC-12-1` / `AC-12-1`）。番号だけの
id は、PR や判断の記録に引用されたときにアプリ共通の通し番号に見える。

### 節ごとに書くもの

1 つの決定が 3 つの節に書かれた実例があるので、節の分担を守る。

| 節 | 書くもの | 書かないもの |
|---|---|---|
| ユーザーストーリー | この変更で誰の何が良くなるか。1〜3 個。issue の言い換えで足りるなら 1 行 | 手段（「〜を実装する」）。issue から読み取れない受け手。INVEST の自己申告 |
| 要件の詳細化 | issue の語の解釈（何を指しているか） | 決めたこと |
| 対象の画面 | 場所の一覧。パスは**実在するルーティングから引く**。画面を持たない変更なら出口（API の応答・CLI の出力・生成物）を書くか「該当なし」 | 操作したときの振る舞い |
| ユースケース | 振る舞いの一覧。「誰が何をすると、いまどうなり、これからどうなるか」を 1 行。変えない振る舞いも、変える対象と紛らわしいなら書く | 検証手順 |
| 前提 | 「決めたこと」（判断の記録の `<slug>` を添えて 1 行）と「未確認」（行ごとに本文での残し方）を別の表に。1〜2 行なら箇条書きでよい | 決めた理由（判断の記録にある）。変更対象と重なること。**判明済みの持ち越し**（未確認ではない） |
| 実装方針 | 順序。何を先にやり、何がその前に要るか。理由が自明でないときだけ表の下に散文 | ファイルごとの変更内容。成果物の中身（developer が決める） |
| 受け入れ条件 | ストーリーと AC の対応表 | 表を埋めるための当たり障りのない条件 |
| 変更対象 | ファイルごとの種別（`新規` / `変更` / `削除` / `テスト` / `生成物`）と変更内容。`生成物` はどのコマンドが作るか | 順序と理由 |
| 規模判定 | 変更対象の種別を数えた 2 つの数 | 下の「規模判定」を見る |

- **計画は実装方針であって実装ではない。** コードの断片・受け入れ条件の重複・調べた過程を書かない。
  200 行を超えたら、実装を書いているか、分割すべき規模になっている
- 差し戻しのラウンドでは、前回書いたことを書き直さない

### 大きくしない（分割の 3 軸）

ストーリーが 4 つ以上になる、または 1 PR（目安はテストを除いて 20 ファイル、含めて 40 ファイル）に
収まらないなら、分ける合図である。次の軸で切り、**この計画で出すストーリーだけを残す**。
残りは `## 規模判定` に分割案として、どの軸で切ったかと一緒に書く（分けるかは人間が決める）。

| 軸 | 切り方 | 例 |
|---|---|---|
| 正常系 / 異常系 | まず正常系だけを出す | 「登録できる」→「重複や失効のときの扱い」 |
| CRUD | 参照 → 追加 → 更新 → 削除 | 「一覧が見える」→「登録できる」→「直せる」 |
| アクター | 受け手ごとに切る | 「利用者が見られる」→「運用者が直せる」 |

切る順は価値が先、依存が先。分けた 1 つ 1 つが、それ単体で受け手に届いて意味を持つかを確かめる
（同じ作業を細かく割って往復を増やすのが目的ではない）。

### 規模判定

- **上限を超えると判断したときだけ `上限超過` と書き**、分割案を続ける。上限以内なら、否定形
  （「上限超過ではない」）も含めてこの語を書かない — ハーネスは語の有無で PR に警告を出す
- `上限超過` と書いても実装は進む。そのまま実装できる状態まで計画を完成させる
- **この PR だけでは issue を閉じ切れないなら**、その旨と「issue が閉じるのはどの PR か」を 1 行書き、
  PR 本文では `Closes #<n>` ではなく `Refs #<n>` を使うよう実装方針に書く（後片付けを次の PR に
  回すと、merge しても issue は終わらない）

## `acceptance.json`

**JSON で**書く。

```json
{
  "criteria": [
    {
      "id": "AC-12-1",
      "description": "Foo は期限切れのとき nil を返す",
      "verification": "automated",
      "command": "bin/rails test test/models/foo_test.rb -n /expired/",
      "status": "pending",
      "evidence": null
    },
    {
      "id": "AC-12-2",
      "description": "既存セッションの挙動が変わらない",
      "verification": "manual",
      "status": "pending",
      "evidence": null
    }
  ]
}
```

- **`description` は命題、`command` はその証明手段。** 満たしたかどうかが判定できる文にする
  （「適切に処理する」は不可）。この順序を崩すと、コマンドが通っても条件を満たした証明にならない
- **`command` はその条件を特定できる最小の呼び出し**（ファイル + テスト名の絞り込み）。スイート全体だけ
  では、緑でもその条件を検証したとは言えない。規約（`.agent/conventions.md`）の「テスト」節と
  食い違う形にしない
- **テストはまだ存在しない。** `command` は予言で、名前が変わったら developer が直して判断の記録に残す
- **走らせられないなら `manual`。** このパイプラインは `automated` を自分で実行しないので、DB や
  サービスが要るテストは `manual` になる。**その前に配布先の CI（`.github/workflows/*.yml`）を読む** —
  system test・E2E が走っているなら、テストは書いたうえで `manual` にし、`evidence` に引くジョブ名を書く
- **金額・数量・件数は 0・負・上限のどれかを 1 件は踏む。** 正常な 1 ケースだけの条件は、実在する
  データ（損の出る取引、0 件、桁あふれ）で落ちる
- **保存済みのデータの意味を変える変更では、変更前のデータが入った状態を条件にする**（fixture か
  setup での直接更新）。空のデータでしか確かめない計画は、移行できていることを示せない
- `status` は全項目 `pending`、`evidence` は `null`。更新するのは developer
